# 商品运营看板需求说明

## 1. 背景

平台的核心业务是把店铺商品资料和店铺位置信息纳入知识库，用户通过 AI 搜索查询商品详情及所在店铺。现有管理看板的“高频问题”按完整问题文本聚合，同一商品的不同问法会被拆成多条，无法反映真实商品热度。

## 2. 目标

- 管理员可查看统计周期内的商品查询量、商品匹配情况和未匹配查询。
- “高频问题”调整为“热门商品”，同一商品的不同问法按商品实体合并。
- 热门商品数据必须来自真实 RAG 最终引用，不使用固定样例或关键词猜测。
- 部门管理员只能查看本部门数据，超级管理员可查看全部部门或指定部门。
- 指标记录不得保存用户原问题、答案正文或其他敏感内容。

## 3. 统计口径

### 3.1 商品实体

当前系统尚无独立商品主数据表，因此使用 RAG 最终引用中排名第一的文档作为本次问答的“主商品”：

- 商品标识：最终第一条引用的 `doc_id`。
- 商品名称：最终第一条引用的 `doc_title`。
- 推荐数据规范：一个商品对应一份文档，文档中同时维护商品详情和店铺位置信息。

如果一个问题涉及多个商品，只给排名第一且实际展示给用户的引用商品增加一次查询计数，避免候选文档造成重复或虚高。

### 3.2 指标

- 商品查询量：统计周期内完成的 RAG 回答请求数。
- 已匹配商品查询：存在最终引用，且完成生成或命中缓存的回答数。
- 未匹配商品查询：无最终引用、未生成且未命中缓存的回答数。
- 商品匹配率：已匹配商品查询数 / 商品查询量。
- 热门商品：按主商品标识聚合的问答次数，按次数和最近查询时间倒序。
- 商品资料处理成功率：统计周期内商品资料处理成功数 / 已结束处理数。
- 商品检索评测命中率：来自真实检索测试运行，不等同于答案正确率。

## 4. 验收标准

1. 用户用不同句式询问同一商品，只要最终第一引用为同一文档，热门商品只出现一行，查询次数累加。
2. 不同商品即使问题文本相似，也按不同文档标识分别统计。
3. 无引用回答不进入热门商品统计，并计入未匹配商品查询。
4. 多知识库检索仍按最终第一引用确定商品，不受知识库选择顺序影响。
5. 管理看板不再展示“高频问题”或完整用户问题文本。
6. 历史指标没有商品标识时不伪造归属；升级后的新问答开始形成商品热度。
7. 后端单元测试、PostgreSQL 聚合测试、前端组件测试、类型检查和构建通过。

## 5. 限制

- 当前商品身份依赖文档粒度。若一份文档包含多个商品，无法稳定拆分商品热度；后续应引入商品主数据表及商品与文档映射。
- 店铺位置目前保存在文档正文中，系统没有结构化地址字段，因此本期不展示可能失真的“位置完整率”。
